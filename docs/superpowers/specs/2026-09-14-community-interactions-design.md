# 第四阶段：视频社区互动闭环设计

## 目标

在第三阶段已经完成的注册登录、视频直传、Kafka 异步转码、MinIO HLS 存储和浏览器播放基础上，增加公开发布、互动和个人内容管理，让用户能够完成“发现视频、观看、互动、关注作者、回看个人记录”的完整业务流程。

本阶段继续采用 Gin 模块化单体和 MySQL 强一致事务。Redis、异步统计、推荐算法、go-zero 微服务与 Kubernetes 留到业务闭环稳定后的阶段。

## 方案选择

### 方案 A：模块化单体 + MySQL 事务（采用）

互动关系和统计在一个数据库事务内写入。唯一索引负责防止重复点赞、收藏和关注，接口保持幂等。优点是行为明确、容易学习和测试，也与当前项目分层一致；缺点是高并发统计能力有限，后续需要把热点计数迁移到 Redis 或 Kafka。

### 方案 B：Kafka 异步更新统计

点赞等关系先落库，再发送事件异步更新计数。吞吐量更高，但页面会短暂显示旧数字，还需要处理重复消息、消费失败和数据校准。本阶段业务量与复杂度都不需要这一方案。

### 方案 C：go-zero 微服务 + Redis

提前拆出互动、评论、关系和视频服务。它能展示服务治理技术，但会同时引入 RPC、分布式事务、服务发现和部署复杂度，在业务边界尚未稳定时收益较低。

## 范围

### 视频发布与管理

- `ready` 表示媒体已经成功转码，可以播放；`visibility` 表示作者是否允许公开访问。
- 已有视频迁移后默认为公开，避免当前可播放视频从发现页消失。
- 作者可以修改标题、简介和公开状态，可以逻辑删除自己的视频。
- 发现页和公开详情只返回 `ready + public` 视频。
- 私有、删除、上传中、处理中和失败的视频只能由作者通过“我的投稿”查看状态，不能通过公开接口播放。

### 互动

- 登录用户可以点赞、取消点赞、收藏、取消收藏。
- 登录用户可以关注、取消关注其他用户，不能关注自己。
- 登录用户可以发表评论并删除自己的评论；本阶段使用平铺评论，不做楼中楼、审核后台和消息通知。
- 重复的点赞、收藏、关注和取消操作都返回成功后的最终状态，不产生重复数据或错误计数。

### 观看记录与播放量

- 登录用户开始播放时上报一次观看，后续可以上报播放进度。
- `watch_histories` 对每个“用户 + 视频”只保留一条记录，重复观看更新进度和最后观看时间。
- 同一登录用户对同一视频只贡献一次累计播放量。匿名访问可以浏览和播放，但本阶段不计入播放量，从而避免使用 IP 进行不可靠且涉及隐私的去重。

### 个人中心

- 查看自己的投稿、收藏、观看历史和关注列表。
- “我的投稿”提供编辑、公开/私有切换和删除操作。

### 搜索

- 发现页可以按视频标题、简介、作者用户名和作者昵称搜索。
- 关键词去除首尾空白后最长 50 个字符；空关键词等同于普通发现列表。
- 搜索只返回 `ready + public` 视频，并且可以继续使用最新/热门排序和分页。
- 第一版使用 MySQL `LIKE` 模糊匹配，以便直接支持中文关键词；Repository 必须转义 `%`、`_` 和转义符本身，不能把用户输入直接拼接进 SQL。
- 当前数据规模下接受前置通配符查询的成本。数据量增长后再通过相同 Service 接口替换为 Meilisearch 或 Elasticsearch，不改变前端 API。

## 数据模型

### `videos` 扩展

- `visibility TINYINT NOT NULL DEFAULT 1`：`1` 公开，`2` 私有。
- `published_at DATETIME(3) NULL`：第一次具备公开播放条件的时间。
- 保留现有处理状态字段；逻辑删除继续使用 `status = deleted`。

### `video_stats`

- `video_id`：主键并外键关联 `videos.id`。
- `view_count`、`like_count`、`favorite_count`、`comment_count`：无符号计数，默认 0。
- `updated_at`：最后更新时间。

### `video_likes` 与 `video_favorites`

- 复合主键 `(user_id, video_id)`，保证关系唯一。
- `created_at` 记录操作时间。
- 用户或视频删除时级联清理。

### `comments`

- `id`、`video_id`、`user_id`、`content`、`created_at`、`updated_at`、`deleted_at`。
- 内容去除首尾空白后长度为 1–500 个字符。
- 删除采用软删除，计数只包含未删除评论。

### `user_follows`

- 复合主键 `(follower_id, followee_id)`。
- 数据库检查约束和业务校验共同阻止关注自己。

### `watch_histories`

- 复合主键 `(user_id, video_id)`。
- `progress_ms`、`duration_ms`、`first_watched_at`、`last_watched_at`。
- 第一次插入时增加播放量，后续上报只更新记录。

所有表使用外键和必要索引；迁移提供 Up 与 Down，已经发布的迁移文件不修改。

## 后端结构

- 扩展 `internal/video`：公开条件、排序、作者编辑和删除。
- 新增 `internal/engagement`：点赞、收藏、评论、观看历史与视频统计。
- 新增 `internal/follow`：关注关系和关注列表。
- Handler 只处理 HTTP 参数、认证信息和响应映射；Service 执行业务规则；Repository 封装 GORM 查询与事务。
- 为公开详情增加可选鉴权。未携带 Token 时仍可访问；携带有效 Token 时返回 `liked`、`favorited`、`following_author` 等当前用户状态。无效 Token 按未认证处理，写接口仍使用强制鉴权。

## API

### 公开读取

- `GET /api/v1/videos?q=&page=&page_size=&sort=latest|popular`
- `GET /api/v1/videos/:id`
- `GET /api/v1/videos/:id/comments?page=&page_size=`

视频响应增加 `stats`；登录后的详情响应增加 `viewer_state`。

### 视频作者操作

- `PATCH /api/v1/users/me/videos/:id`：修改标题、简介或公开状态。
- `DELETE /api/v1/users/me/videos/:id`：逻辑删除。

### 点赞、收藏和观看

- `PUT /api/v1/videos/:id/like`、`DELETE /api/v1/videos/:id/like`
- `PUT /api/v1/videos/:id/favorite`、`DELETE /api/v1/videos/:id/favorite`
- `POST /api/v1/videos/:id/watch`：创建或更新观看历史与进度。

### 评论

- `POST /api/v1/videos/:id/comments`
- `DELETE /api/v1/comments/:id`

### 关注

- `PUT /api/v1/users/:id/follow`
- `DELETE /api/v1/users/:id/follow`

### 个人数据

- `GET /api/v1/users/me/favorites`
- `GET /api/v1/users/me/history`
- `GET /api/v1/users/me/follows`

分页默认 12 条，最大 50 条。资源不存在、不可公开访问或不属于当前用户时返回统一错误码，不泄露私有资源信息。

## 前端设计

继续使用现有原生 HTML、CSS、JavaScript 和同源 Node 代理：

- 发现页增加最新/热门排序，并在卡片上显示播放、点赞、评论数据。
- 发现页增加搜索表单、清空按钮、加载状态和无结果提示；提交搜索或切换排序后回到第一页，翻页时保留当前关键词和排序。
- 详情页保留 HLS 播放器，增加作者信息、关注、点赞、收藏和评论区域。
- 视频真正开始播放时上报观看；播放过程中节流上报进度，离开页面前尽力提交最后进度。
- 导航增加“我的”入口，内部切换投稿、收藏、历史和关注。
- “我的投稿”提供编辑信息、公开状态切换和删除确认。
- 未登录用户可以浏览和播放；点击互动按钮时显示清晰的登录提示。

## 正确性与错误处理

- 点赞、收藏、关注和首次观看使用唯一键与事务实现幂等。
- 关系写入/删除和 `video_stats` 增减在同一事务内完成，计数使用数据库表达式并保证不会减为负数。
- Service 每次互动前确认视频为公开可播放状态；作者管理操作确认资源所有权。
- 评论删除只有评论作者可以执行。
- 所有请求校验页码、排序、ID、搜索关键词、文本长度和观看进度范围。
- 搜索查询使用参数绑定并转义 MySQL `LIKE` 通配符；任何关键词都不能改变 SQL 结构。
- 存储和转码链路保持不变；逻辑删除暂不立即删除 MinIO 文件，后续由对象清理任务处理。

## 测试与验收

1. 迁移 Up 后新表、外键、唯一索引和默认数据正确，Down 可以逆向移除本阶段结构。
2. Service 单元测试覆盖成功、重复操作、无权限、资源不可见和计数边界。
3. Repository 集成测试覆盖事务、并发唯一关系、分页、搜索通配符转义、作者字段搜索和历史记录 Upsert。
4. Handler 测试覆盖认证、参数校验、状态码和响应结构。
5. 前端测试覆盖搜索、清空、排序、翻页状态保持、互动状态切换、评论渲染、个人列表和错误提示。
6. 自动化测试通过后，使用两个真实测试账号验收：A 发布视频；B 能通过标题和作者搜索到该视频，并完成观看、点赞、收藏、评论和关注；A 能看到正确统计并管理投稿；B 能在收藏、历史和关注中找到对应内容；取消操作后关系和计数正确。

## 后续演进边界

第四阶段完成后，第五阶段再引入 Redis 处理热点统计、限流和热门榜单，并通过 Kafka 异步落库与校准；之后再评估 go-zero 服务拆分、Kubernetes 部署和 AI 内容能力。
