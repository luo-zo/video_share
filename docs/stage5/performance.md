# T12 本地性能基线

## 状态与范围

本文记录可复跑的隔离环境 API 基线，不代表生产容量测试。压测对象是分类列表、日榜和公开视频评论列表；视频分片下载与 FFmpeg 转码不包含在这些 QPS/P95 数字里。冷缓存单次请求的 P95/P99 不具备统计意义，只作为冷启动样本单独报告。

运行入口（仓库根目录，Windows PowerShell 5.1）：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File perf/run-stage5-bench.ps1 -Mode smoke
powershell.exe -NoProfile -ExecutionPolicy Bypass -File perf/run-stage5-bench.ps1 -Mode baseline -VUs 5 -Duration 15s -Repeat 3
powershell.exe -NoProfile -ExecutionPolicy Bypass -File perf/run-stage5-bench.ps1 -Mode stress -VUs 10 -Duration 15s -Repeat 3
powershell.exe -NoProfile -ExecutionPolicy Bypass -File perf/run-stage5-bench.ps1 -Mode media -VUs 3 -Duration 15s -Repeat 3
```

脚本只接受本机 `127.0.0.1:18081` API 和名称为 `stage5-smoke-*` 的显式隔离 Compose 项目；不会启动/重建服务。正式 API 基线比较：分类与榜单各三次冷缓存（精确删除其单个 cache key，每次 1 个请求）、三次热缓存、三次 Redis 不可用的回退（5 VU、15 秒）；评论读取在 Redis 恢复后三次执行（5 VU、15 秒）。另外对三个读取接口以 10 VU 做三次递增压力复测。媒体模式另以 3 VU、15 秒重复三次读取隔离公开视频的一个 HLS MPEG-TS 分片；其签名 MinIO 地址指向本机映射端口，因此只在这个 k6 容器上使用 Docker Desktop host networking。持续场景每次请求后固定 sleep 100 ms，把 3/5/10 VU 循环负载限制在约 30/50/100 req/s，而不是让 VU 无等待地打满本机。Redis outage 使用 `finally` 恢复，匿名评论写权限探针在计时 workload 之外，预期 HTTP 401，不创建业务行。

### 观测口径限制

- k6 JSON 是每次运行的原始摘要；冷缓存每次只有一个请求，不将该样本伪装成稳定 P95/P99。
- MySQL `Questions` 和 Redis `INFO stats` 是容器级全局计数差，包含健康检查、后台榜单重建及可能的其它本机请求；不是某个 handler 的精确 SQL / Redis 命令数。
- Docker CPU / 内存由 `docker stats` 大约每秒采样。CPU 汇总是容器采样平均/峰值；内存字段是采样期间观察到的峰值，不是精确进程剖析或宿主机总负载。
- 评论接口没有 Redis 缓存，单独作为 MySQL-backed engagement read；未对登录评论写入做负载，以免制造无界合成评论。匿名写入拒绝通过独立 401 检查。
- HLS 仅测了单个 360p MPEG-TS 分片的重复读取；未测多码率切换、整段播放连续性、并发上传、真实公网延迟、长时间稳态/峰值或硬件 FFmpeg throughput。不得用本报告推导生产容量或“提升百分比”。
- 预检中有一轮无 pacing 的初始实现曾达到约 1,700 req/s（5 个 VU），且榜单预热命令未指定 `RANKING_REBUILD_ONCE=1`。该轮已中止并从基线排除；仅终止了由这次 runner 启动的两条多余一次性 CLI 子进程，长驻 ranking service 和数据库未停止/清理。正式 runner 已加入 100 ms VU pacing 与 one-shot rebuild。

## 转码样本

使用 T11 真实依赖 E2E 中的合成固定视频，与 API k6 指标分开。隔离 MySQL `video_transcode_jobs` 记录的 `created_at → started_at → finished_at` 对应 job 入队、Worker claim、Worker 成功提交：视频 ID 28，时长 8,000 ms，640×360，Worker `docker-worker-1`，attempts=1；排队 706 ms，claim 到成功 855 ms，入队到成功 1,561 ms。原始行见 [transcode-sample-20260924.csv](perf-results/transcode-sample-20260924.csv)。

Worker Compose 部署为 1 个 consumer。`backend/cmd/worker/consume.go` 对 Poll 返回的 records 顺序循环并同步调用 `Process`，没有进程内并行 worker 配置；job 的 855 ms 包括源文件下载、FFprobe、FFmpeg/HLS 产物生成和 MinIO 上传，不是纯 FFmpeg CPU 时间。样本来自一次 8 秒 synthetic fixture，不是吞吐或可扩展性结论；纯 FFmpeg 子阶段、分片服务吞吐及多个 Worker 横向并发尚未测。
